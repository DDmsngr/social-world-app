# Перенос из Instagram, календарь фото, место и время снимка

Проект решения: три связанные задачи.

1. Перенести свои публикации из Instagram с исходными датами.
2. Календарь фото: публикации разложены по дням, когда были сделаны.
3. У каждой публикации сохраняются место и время снимка. Автор всегда видит их у себя на карте, другие — только то, что он разрешил. Гео можно запретить совсем, и в настройках поста это должно быть сразу видно.

Все три задачи держатся на одной модели данных — «когда и где снято» отдельно от «когда опубликовано» и «кому это видно». Поэтому начинаем с неё.

---

## 0. Что уже есть и что надо исправить до всего остального

**Утечка через EXIF — исправить первым делом.** `MediaUploader.upload` отправляет файл в публичный бакет как есть. `image_picker` на Android при сжатии (`imageQuality: 85`) переносит EXIF в новый файл, GPS-теги тоже. Выходит, что при выключенном «Показывать место публикации» координаты всё равно доступны любому, кто скачает фото по ссылке. Надо так:

- до загрузки прочитать из файла дату и GPS (они пригодятся для раздела 1);
- затем перекодировать файл без метаданных (GPS, модель камеры, серийный номер, миниатюра) и загружать уже чистый;
- в тесте проверять, что в загруженном файле не осталось ни одного GPS-тега.

**Что есть в схеме сейчас:**

| Поле | Что это | Проблема |
|---|---|---|
| `posts.created_at` | время создания строки | для переноса нужно время из Instagram, а для календаря — время снимка |
| `posts.place_id` | ссылка на справочник мест | фото сняли не обязательно у «места» из справочника |
| `posts.geo`, `blur_m` | колонки из 0001, клиент их не заполняет | подходят для размытой точки, но только для неё |
| `posts.show_geo` | да/нет | двух состояний мало: нужны «никому», «город», «район», «точно» |

## 1. Модель данных

### 1.1. Время: три разных момента

| Поле | Смысл | Откуда берётся |
|---|---|---|
| `taken_at` | когда снято | EXIF `DateTimeOriginal`; для переноса — время из архива Instagram; если нет ничего — `published_at` |
| `published_at` | когда пост появился у автора | обычный пост — `now()`; перенесённый — дата публикации в Instagram |
| `created_at` | когда строка создана у нас | всегда `now()`, служебное |

Календарь строится по `taken_at`, лента — по `published_at`. Поэтому перенос 800 старых постов не затопит ленту подписчиков: у них даты 2016–2025 годов, и в ленту сверху они не попадут.

`taken_at_source`: `exif` / `import` / `manual` / `publish_time` — чтобы в посте можно было честно подписать «дата со снимка» или «дата публикации».

Часовой пояс: храним `timestamptz` и отдельно `taken_tz` (смещение из EXIF `OffsetTimeOriginal`, если есть). Иначе фото, снятое в 23:30 во Владивостоке, попадёт в календаре москвича на предыдущий день. День в календаре = локальная дата снимка там, где его сделали.

### 1.2. Место: точка съёмки отдельно от того, что видят другие

Предлагаю две таблицы с разными правами доступа.

```
post_geo_private          -- видит только автор
  post_id     uuid pk → posts
  author_id   uuid
  geo         geography(point)   -- точка съёмки
  accuracy_m  integer            -- точность GPS, если известна
  source      text               -- exif | import | device | manual

posts (новые/изменённые колонки)
  geo_visibility text  -- hidden | city | area | exact   (заменяет show_geo)
  geo        geography(point)    -- уже есть: то, что видят другие (размытое/точное)
  blur_m     integer             -- уже есть
  geo_city   text                -- название города для уровня «город»
```

- RLS на `post_geo_private`: select/insert/update/delete только `auth.uid() = author_id`. Ни одна `security definer` функция не отдаёт эту таблицу чужим.
- Публичную точку `posts.geo` считает клиент (как сейчас `GeoPrivacy.blur`) при публикации и при каждой смене уровня видимости:
  - `hidden` → `geo = null`, `geo_city = null`
  - `city` → `geo = null`, `geo_city = 'Сочи'`
  - `area` → размытая точка, радиус из настроек профиля (200 / 500 / 1000 / 3000 м)
  - `exact` → точка съёмки как есть
- `city_feed` отдаёт чужим только `posts.geo` / `geo_city` и только по `geo_visibility`, автору — ещё и точку из `post_geo_private`.

> ⚠️ **Решение за вами.** Первая миграция закрепила принцип «точных координат в базе нет» (152-ФЗ). Точка съёмки, видимая автору, этот принцип нарушает — пусть и в таблице, которую видит только он. Варианты:
>
> - **A (рекомендую).** Храним точку в `post_geo_private` под RLS «только автор». Карта автора работает на любом устройстве и переживает переустановку. Объём персональных данных растёт, и в политике конфиденциальности это нужно описать. Сервера и так стоят в РФ.
> - **B.** Точка съёмки живёт только на устройстве (локальная БД), в базу уходит размытая. При смене телефона точность пропадёт: на карте автора останется размытая точка.
> - **C.** Как в A, но точку шифрует ключ устройства (как в чатах). Сервер её не читает, зато нужен перенос ключей между устройствами.

### 1.3. Происхождение поста

```
posts
  source        text   -- app | instagram
  source_id     text   -- id медиа в архиве Instagram (для идемпотентности)
  unique (author_id, source, source_id) where source_id is not null
```

Благодаря уникальному индексу повторный перенос того же архива не создаёт дублей: на такой вставке срабатывает `on conflict do nothing`.

### 1.4. Миграция существующих данных

- `geo_visibility = case when show_geo then 'area' else 'hidden' end`. Для старых постов с местом из справочника — `exact`: место и так публичное.
- `published_at = created_at`, `taken_at = created_at`, `taken_at_source = 'publish_time'`.
- `show_geo` оставить на один релиз как вычисляемое поле (`geo_visibility <> 'hidden'`), чтобы старые клиенты не сломались, потом удалить.
- Разрешить автору `update (taken_at, geo_visibility, geo, blur_m, geo_city)`; `published_at`, `source`, `source_id` через PATCH не менять.
- Rate-limit на вставку постов (`posts_rate_limit` из 0015) перенос упрётся сразу. Нужен отдельный путь: RPC `import_posts(batch jsonb)` — до 50 постов за вызов, с собственным суточным лимитом.

## 2. Перенос из Instagram

> **Требование (30.09):** минимум движений. Сценарий «скачай архив по ссылке, потом залей его сюда» — слишком сложный и не годится. Истории тоже переносим, если это технически возможно.

> **Решение (30.09, второе):** стартуем в РФ, Instagram там запрещён. Поэтому **никакой интеграции с Instagram с нашей стороны**: ни API, ни встроенного браузера, ни глубоких ссылок в Instagram. Даём **инструкцию**, человек сам получает архив, а перед переносом **принимает согласие**: за перенесённый контент отвечает он, а не мы. Ниже (2.1–2.4) — прошлые варианты для истории. Актуальный сценарий — в 2.0.

### 2.0. Актуальный сценарий: инструкция + согласие

**Что меняется по сравнению с 2.2:**
- Убираем глубокую ссылку в Instagram и скачивание во встроенном браузере: это уже активное содействие, а не разбор файла пользователя.
- Instagram в РФ открывается через VPN, а наше приложение при переключении VPN теряет соединение (см. `vpn_check.dart`: после выключения VPN нужен перезапуск). Значит, архив человек получает **вне нашего приложения**, а потом приносит файл к нам — это естественное разделение.

**Шаги для человека:**
1. В приложении: «Перенести фото из архива соцсети» → экран-инструкция: 3–4 шага с картинками, как заказать архив (формат JSON, «всё время», высокое качество). Кнопок, открывающих Instagram, нет — только текст и скриншоты.
2. Человек заказывает архив, получает письмо, скачивает ZIP.
3. Переносит его к нам в одно касание: «Поделиться → Social World» / «Открыть в Social World» из уведомления о загрузке, или наш выбор файла сразу открывается в «Загрузках» со свежим архивом наверху.
4. **Экран согласия** (ниже) — галочка + «Принимаю». Без этого разбор архива не начинается.
5. Предпросмотр → «Перенести» (по умолчанию «Только мне», место скрыто) → перенос в фоне.

**Галерея телефона (2.3)** остаётся как мгновенный старт: она с Instagram вообще не связана, юридически чистая.

### 2.0.2. Честно: что согласие закрывает, а что нет

Согласие нужно и полезно, но **ответственность целиком на пользователя не перекладывает**. Для записи, чтобы обсудить с юристом:

- **Запрещённый контент.** Как площадка мы всё равно обязаны реагировать на жалобы и требования об удалении (149-ФЗ, а при большой аудитории — обязанности соцсети по 530-ФЗ). Значит, перенесённое проходит через те же жалобы и модерацию, что и обычные посты. Согласие это не отменяет, но переносит на пользователя ответственность перед третьими лицами.
- **Чужие люди на фото.** Их согласия пользователь дать не может. Поэтому по умолчанию «Только мне» — это не только приватность, но и юридическая страховка.
- **Упоминание Instagram.** Внутри приложения — нейтрально: «архив соцсети». Если название Instagram где-то всё же нужно (в инструкции со скриншотами оно неизбежно видно) — со сноской «принадлежит Meta, признанной экстремистской и запрещённой в РФ». **Никаких логотипов** Instagram/Meta в интерфейсе, иконках и сторах.
- **Инструкция со скриншотами.** Серая зона: она показывает, как пользоваться заблокированным сервисом. Не упоминать VPN и способы обхода блокировок вообще — ни в тексте, ни в картинках (реклама обхода блокировок запрещена).
- **Сторы.** В описании приложения в RuStore / Google Play / App Store функцию называть «Перенос фото из архива», без Instagram.

**Для юриста — три вопроса:** достаточно ли инструкции без брендинга; нужна ли сноска Meta на экране инструкции; устраивает ли формулировка п. 5 согласия.

### 2.3. Параллельно: мгновенный старт из галереи

Пока Instagram готовит архив (или если человек не хочет с ним возиться):
- «Показать мои фото в календаре?» → доступ к галерее → календарь и карта заполняются сразу по EXIF (дата и место съёмки).
- Эти фото **не публикуются** и не загружаются на сервер — это личный слой календаря на устройстве. Опубликовать фото из календаря можно одним нажатием.
- Когда приходит архив Instagram, фото из галереи и из Instagram сопоставляются (по дате и похожести картинки), чтобы в календаре не было дублей.

Так человек получает «вау, моя жизнь на календаре» в первую минуту, а Instagram догружается позже.

### 2.4. Профессиональные аккаунты — вариант А как бонус (под вопросом)

Для авторов и бизнес-аккаунтов можно сделать кнопку «Войти через Instagram» — перенос постов без ожидания. Но: без историй и без геометок, с проверкой приложения в Meta и **юридическим риском в РФ**. Решать только после консультации с юристом. Для MVP не нужен.

> ⚠️ **Юридический момент.** Meta признана в РФ экстремистской организацией, Instagram заблокирован. Разбор файла, который принёс сам пользователь, — меньший риск, чем интеграция с API, но формулировки и логотип в интерфейсе стоит согласовать с юристом. Нейтральный вариант — «Перенести из архива соцсети».

### 2.5. Что лежит в архиве (формат JSON)

```
your_instagram_activity/content/posts_1.json   — посты (карусели — массив media)
your_instagram_activity/content/reels.json      — рилсы
your_instagram_activity/content/stories.json    — архив историй
media/posts/YYYYMM/*.jpg|*.mp4                  — файлы постов
media/stories/YYYYMM/*.jpg|*.mp4                — файлы историй
```

У каждого поста: `media[].uri` (путь внутри архива), `creation_timestamp` (unix, UTC), `title` (подпись). У части медиа есть `media_metadata.photo_metadata.exif_data[]` с `latitude`/`longitude` и `date_time_original`. Геометку поста («место» в Instagram) архив отдаёт нестабильно — на неё не рассчитываем.

Формат архива Meta меняет без предупреждения: пути и ключи плавают. Поэтому парсер:

- ищет файлы по маске (`**/posts_*.json`), а не по жёсткому пути;
- не падает на незнакомых полях и отсутствующих ключах;
- чинит «моджибейк» — Meta пишет кириллицу как latin-1 поверх UTF-8 (`Ð\u009f` вместо «П»);
- покрыт тестами на нескольких реальных (обезличенных) архивах разных лет.

Если архив в HTML, а не JSON, просим заказать заново и показываем, где переключить формат.

### 2.6. Истории

**Да, переносим** — из архива (вариант Б). Через API (вариант А) архива историй нет.

- Попадают только истории из архива Instagram. Архив историй в Instagram включён по умолчанию, но если человек его выключал — тех историй нет и у Meta.
- У нас истории — не отдельный формат, живущий 24 часа, а **воспоминания в календаре**: в дне видны и посты, и истории этого дня. В ленту и в «истории» подписчиков они не попадают.
- Видимость по умолчанию — «Только мне», как у всего перенесённого.
- Интерактив не переносится: опросы, ссылки, музыка, отметки людей. Переносится картинка или видео.
- Истории обычно дают основной объём: тысячи файлов. Поэтому при предпросмотре — отдельная галочка «Истории (1 900)», включённая по умолчанию, чтобы можно было перенести только посты, если мало места.

### 2.7. Какие даты ставить

| Поле | Значение |
|---|---|
| `published_at` | `creation_timestamp` поста |
| `taken_at` | `exif_data.date_time_original`, если есть и не позже `published_at`; иначе `creation_timestamp` |
| `taken_at_source` | `exif` или `import` |
| точка съёмки | `exif_data.latitude/longitude`, если есть и не равны `0,0` |

Карусель = один пост с несколькими медиа. `taken_at` поста — самое раннее из медиа, а свой `taken_at` у каждого медиа хранится в `post_media` (см. 3.3), чтобы в календаре фото из поездки разошлись по своим дням.

### 2.8. Ограничения, о которых говорим честно

- Лайки и комментарии не переносятся: они принадлежат другим людям.
- Отметки людей не переносятся: у нас нет соответствия аккаунтов.
- Видео длиннее нашего лимита (сейчас минута) переносятся первым фрагментом или пропускаются — решить. Предлагаю пропускать и показывать список пропущенного.
- Первая версия — Android и iOS, веб не делаем: ZIP на несколько ГБ в браузере не разобрать.

## 3. Календарь фото

### 3.1. Где живёт

В профиле, рядом с сеткой постов: переключатель «Сетка / Календарь / Карта». Свой профиль — все посты, чужой — только то, что видно по `visibility`.

### 3.2. Как выглядит

- **Месяц**: сетка дней, в ячейке миниатюра первого фото дня и счётчик, если фото больше одного. Пустые дни приглушены.
- **Год**: 12 мини-месяцев с «тепловой» подсветкой дней, где есть фото. Удобно листать перенесённые годы.
- Сверху — быстрый переход по годам: 2016 … 2026.
- **День**: лента фото этого дня по времени. У каждого — время снимка и место (если видно), кнопка «на карте».
- В день попадают посты по локальной дате `taken_at` (с учётом `taken_tz`).

### 3.3. Данные

Отдельная RPC, чтобы не тянуть всю ленту:

```sql
photo_calendar(in_author uuid, in_from date, in_to date)
  returns table (day date, post_count int, cover_url text, post_ids uuid[])
```

Права те же, что у `city_feed`: `can_see_post`, блокировки, модерация. Для дня — `city_feed` с фильтром по диапазону `taken_at`.

Чтобы фото из одной карусели ложились на разные дни, пригодится таблица медиа вместо массива `media_urls`:

```
post_media (post_id, position, url, kind, taken_at, width, height)
```

Первая версия может обойтись без неё и класть пост в день его `taken_at`. Но переносить карусели «из отпуска» без неё выйдет криво, так что заложить её стоит сразу.

### 3.4. Правка даты

Автор может поправить дату снимка (`taken_at_source = 'manual'`) — например, если EXIF врёт или фото отсканировано. `published_at` не меняется никогда.

## 4. Место и время на карте

### 4.1. Что видит автор

- В посте всегда: «📍 Сочи, Морской вокзал · 14 июля 2023, 19:42». Рядом значок уровня видимости: 🔒 «Только вы видите место» / 🏙 «Другие видят: город» / ◎ «Другие видят: район ~500 м» / 📍 «Другие видят: точное место».
- В профиле вкладка «Карта»: все свои фото на карте, кластерами. Точки — из `post_geo_private`. Фильтр по годам, связан с календарём: выбрал день → карта показывает фото этого дня, и наоборот.

### 4.2. Что видят другие

| `geo_visibility` | В посте | На карте |
|---|---|---|
| `hidden` | ничего | нет |
| `city` | «Сочи» | нет (город — не точка) |
| `area` | название района или «рядом с …» | круг радиуса `blur_m`, без точной метки |
| `exact` | название места / адрес | метка |

Время снимка другим показываем с точностью до дня. Точное время вместе с местом раскрывает распорядок человека.

## 5. Настройки приватности гео — чтобы было очевидно

Тема чувствительная, поэтому правила интерфейса такие:

### 5.1. В посте (создание и правка)

Сейчас гео спрятано в свёрнутой панели «Настройки публикации» одним чекбоксом. Так нельзя. Меняем:

- **Строка места всегда на виду** — не в свёрнутой панели, а прямо над кнопкой «Опубликовать»:
  `📍 Место снимка: Морской вокзал` → `Видят: только вы ▾`
- Нажатие открывает лист с четырьмя вариантами. У каждого — пример того, как это увидят другие, и мини-карта с точкой или кругом:
  - **Никому** — «Место видите только вы»
  - **Город** — «Другие увидят: Сочи»
  - **Район** — «Другие увидят круг ~500 м, без точки»
  - **Точное место** — «Другие увидят точку на карте»
- Если выбрано **«Точное место»**, а точка ближе 300 м к месту, которое чаще всего встречается в снимках ночью (вероятно, дом), показываем предупреждение: «Похоже, это рядом с вашим домом. Точно показать?» Вычисляется только на устройстве.
- В сводке настроек и в ленте у собственного поста всегда стоит значок уровня (🔒 / 🏙 / ◎ / 📍) — видно без раскрытия.
- Кнопка **«Удалить место из поста»**: удаляет точку и из `post_geo_private` — автор тоже перестанет её видеть. Спрашиваем подтверждение.

### 5.2. Глобально — «Настройки → Геоданные в публикациях»

Отдельный раздел (сейчас есть только «Приватность геолокации» про присутствие на карте — это другое, их надо развести):

1. **Показывать место другим по умолчанию:** Никому / Город / Район / Точно. Сюда же приходят пресеты публикации.
2. **Никогда не показывать место другим** — главный выключатель. Когда он включён:
   - у всех постов, старых и новых, другие не видят места — проверяет сервер (`city_feed` и RLS смотрят на флаг профиля), а не только интерфейс;
   - уровни в посте заблокированы, рядом надпись «Место скрыто глобально. Изменить в настройках»;
   - сами точки не удаляются, автор по-прежнему видит свою карту.
3. **Не сохранять место снимка вообще.** Координаты вырезаются на устройстве ещё до загрузки: у нас их нет, и автор своих фото на карте тоже не увидит. При переносе из Instagram — то же самое.
4. **Скрыть место у всех моих постов сейчас** — разовое действие: всем постам ставится `hidden`. С подтверждением и числом: «Затронет 812 постов».
5. **Удалить все точки съёмки** — очищает `post_geo_private` целиком. Необратимо, двойное подтверждение.

Флаги 2 и 3 хранятся в `profiles` (`geo_never_public boolean`, `geo_store_taken boolean`), а не в SharedPreferences, иначе на другом устройстве они не сработают.

### 5.3. Проверки на сервере

- `city_feed`, `photo_calendar` и любая будущая функция отдают чужим гео только через одну общую функцию `public_post_geo(post, viewer)`, которая учитывает `geo_visibility`, `geo_never_public` и `can_see_post`. Одна точка правды — меньше шансов забыть проверку в новой RPC.
- Тест в `supabase/tests`: чужой пользователь при каждом уровне видимости и при включённом глобальном запрете не получает ни координат, ни `post_geo_private`.
